# CallbackScheduler — задача с собеседования в Яндекс

## Условие задачи

Реализовать `CallbackScheduler` — планировщик, который принимает коллбэк (`Runnable`) и момент времени (`Instant`), после которого коллбэк должен быть выполнен.

```java
public interface CallbackScheduler extends AutoCloseable {
    void schedule(Runnable callback, Instant after);
}
```

Требования:
- Коллбэк должен выполниться **после** указанного `Instant`, но как можно ближе к нему
- Поддержка множества одновременно запланированных коллбэков
- Потокобезопасность: `schedule()` может вызываться из разных потоков
- Корректное завершение через `close()`

---

## Типичные ошибки

### 1. Polling с `Thread.sleep()`

```
while (running) {
    Thread.sleep(1000);             // <-- бесполезная трата CPU + задержка до 1 сек
    for (task : tasks) {
        if (task.time <= now()) {
            task.run();
        }
    }
}
```

**Проблемы:**
- Задержка выполнения до 1 секунды (гранулярность sleep)
- Потребление CPU впустую на каждом цикле
- Нет приоритета — перебираем все задачи каждый раз

### 2. `ConcurrentHashMap<Instant, Callback>`

```
val taskMap = ConcurrentHashMap<Instant, Callable<CallbackResult>>()
```

**Проблемы:**
- Два коллбэка с одинаковым `Instant` перезапишут друг друга
- Нет упорядоченности — приходится сортировать ключи на каждой итерации
- `toSortedSet()` на каждом тике — лишние аллокации

### 3. Неправильное условие выполнения

```
if (target > Instant.now()) {   // <-- условие наоборот!
    taskMap[target]?.call()
}
```

Задача должна выполняться когда `now() >= after`, а не наоборот.

### 4. Поток не запущен

```
init {
    Thread { ... }   // <-- создали, но не вызвали .start()
}
```

## Правильное решение

### Структуры данных

- **`PriorityBlockingQueue<ScheduledTask>`** — потокобезопасная очередь с приоритетом. Ближайшая по времени задача всегда на вершине. Не нужно сортировать вручную.

### Синхронизация

- **`ReentrantLock` + `Condition`** — рабочий поток спит ровно до момента ближайшей задачи через `awaitNanos()`. При добавлении новой задачи вызывается `signal()`, чтобы поток пересчитал время ожидания.

### Алгоритм рабочего потока

```
while (!stopped):
    1. peek() — смотрим ближайшую задачу (не извлекаем)
    2. Если очередь пуста → await() (ждём новую задачу)
    3. Если время не пришло → awaitNanos(оставшееся время)
    4. Если время пришло → poll() + выполняем коллбэк
```

### Почему `peek()` перед `poll()`?

Если сразу сделать `poll()`, а время ещё не пришло, придётся класть задачу обратно в очередь. `peek()` позволяет сначала проверить время, и извлечь задачу только когда она готова.

### Graceful shutdown

1. `volatile boolean stopped` — видим из всех потоков
2. `signal()` в `close()` — будим рабочий поток
3. `join(5000)` — ждём завершения

## Ключевые концепции многопоточности

| Концепция | Зачем |
|-----------|-------|
| `volatile` | Гарантирует видимость записи из одного потока в другом без лока |
| `ReentrantLock` + `Condition` | Позволяет точно управлять ожиданием (awaitNanos) вместо грубого sleep |
| `PriorityBlockingQueue` | Потокобезопасная очередь с автоматической сортировкой |
| `CountDownLatch` (в тестах) | Ожидание завершения асинхронной операции в тестах |
| `daemon thread` | Поток не мешает завершению JVM |

## Варианты реализации (план для AI-ассистента)

### Вариант 1 — synchronized + wait/notify (приоритетный)
- **Очередь:** обычная `PriorityQueue` — доступ только под `synchronized`
- **Ожидание:** `synchronized(lock)` + `lock.wait(millis)` вместо `Condition`
- **Приватный монитор:** `private final Object lock` — защита от внешней блокировки
- **Shutdown:** `volatile stopped` + `notify()`

### Вариант 2 — ReentrantLock + PriorityBlockingQueue
- **Очередь:** `PriorityBlockingQueue` — потокобезопасная, сортирует по `Instant`
- **Ожидание:** `ReentrantLock` + `Condition.awaitNanos()` — спит ровно до ближайшей задачи
- **Сигнализация:** `signal()` в `schedule()` и `close()` — будит поток при новой задаче или остановке
- **Shutdown:** `volatile stopped` + `signal()` + `join()`

### Вариант 3 — ScheduledExecutorService
- **Всё делает стандартная библиотека:** `Executors.newSingleThreadScheduledExecutor()`
- `schedule()` → `executor.schedule(callback, delay, MILLISECONDS)`
- `close()` → `executor.shutdown()`
- Упомянуть как продакшн-вариант, но на собесе обычно ждут ручную реализацию

### Ключевые вопросы на собеседовании
- **Почему не `Thread.sleep()`?** — задержка до 1 сек, пустая трата CPU
- **Почему не `ConcurrentHashMap`?** — потеря задач с одинаковым `Instant`, нет порядка
- **Зачем `signal()` / `notify()` в `close()`?** — разбудить поток из `await()`, иначе не увидит `stopped`
- **Зачем `volatile`?** — видимость записи между потоками без лока
- **Зачем `peek()` перед `poll()`?** — не извлекать задачу, пока время не пришло
- **Зачем `private Object lock`?** — защита от внешнего `synchronized(scheduler)` и deadlock
- **Альтернатива `signal()` в `close()`?** — `worker.interrupt()`, проще, но грубее
